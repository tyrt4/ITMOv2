# Рефлексия

1. Второй SDD‑фреймворк: GitHub Spec Kit. Выбран из‑за наличия «конституции» и формального цикла spec → plan → tasks → implement; удобен для сравнения с OpenSpec.

2. Применение и сравнение с OpenSpec
- Общее: оба придерживаются принципа «сначала спецификация», артефакты схожи по целям.
- Различия: OpenSpec ориентирован на changes с Why/How/What follows и архивирование; Spec Kit — на constitution и связку spec→plan→tasks. Конституция задаёт жёсткие правила и границы, упрощая проверки.
- Где удобнее: OpenSpec — для быстрых фич; Spec Kit — для выравнивания терминов/ролей и планирования.

3. Две спецификации UI и логики (до кода)
- UI: палитра (#00704A, #D4E9E2, #F1F8F6, #1E3932), типографика (Playfair Display/Inter), layout (sticky header, hero, карточки), тон и отступы.
- Логика: REST API: меню, новости, заказы/оплата, скидки (happy hour/дня), статус магазина, лояльность, отзывы. Формат ошибок: {"detail": "..."}.

4. Реализация и сценарии
- UI и логика работают: фронтенд обращается к API; демо‑данные через /api/v1/dev/seed и data/seed.json. Сквозной сценарий: главная → меню → выбор → быстрый заказ → оплата → проверка статуса заказа. Ошибки/границы: несуществующий menuId → 400; проверка открытости через /api/v1/status/open c now; пустая корзина предотвращается в UI; скидки happy hour/дня применяются (берём максимум).

5. Итоги
- Зафиксировали общий контракт API до реализации. Подкрепили минимальными изменениями, тестами ключевых путей и разделением публичных /api/* от admin /api/v1/*.
